# План реализации встроенного SSH-клиента TamToot

Статус: реализованы профили и импорт ключей (этап 1), зашифрованный транспорт и проверка сервера (этап 2). См. [этап 1](ssh-stage-1.ru.md) и [этап 2](ssh-stage-2.ru.md). Реализован этап 3: пароль, Ed25519/RSA, зашифрованные OpenSSH-ключи, keyboard-interactive и выполнение команд. См. [этап 3](ssh-stage-3.ru.md). Следующий этап — интерактивный терминал. Проверки Windows/Linux и физических устройств, а также независимый аудит собственной криптографии ещё требуются.

## Цель и ограничения

Добавить в TamToot подключение к удалённым серверам, выполнение команд, интерактивный терминал и впоследствии передачу файлов по SFTP.

- Поддерживаемые платформы: macOS, Windows, Linux, Android и iOS.
- Не запускать системные `ssh`, `scp`, `sftp`, оболочки или другие внешние программы для работы клиента.
- Не добавлять сторонние SSH- и криптографические библиотеки. Общая логика протокола реализуется в проекте на Dart.
- Использовать TCP-сокеты и стандартные API платформ. Платформенные адаптеры допустимы для защищённого хранения и криптографических операций, если возможности системных API достаточны.
- Не хранить приватные ключи, парольные фразы и пароли внутри проекта, `.tamtoot`, Git, журналов или истории AI-агента.
- Браузерная сборка не входит в этот план: прямые произвольные TCP-подключения из браузера недоступны без посредника.

Отдельное решение перед разработкой: допускается ли использование системной криптографии через собственные платформенные адаптеры. Отказ и от неё означает необходимость реализации криптографических примитивов в проекте и существенно увеличивает объём работ и требований к проверке.

## Предлагаемая архитектура

| Компонент | Ответственность |
| --- | --- |
| `core/ssh/transport/` | TCP, обмен версиями, бинарные пакеты, таймауты, отмена и ограничения размеров |
| `core/ssh/crypto/` | Интерфейсы криптографии, согласование алгоритмов, обмен ключами, подписи, шифрование и проверка целостности |
| `core/ssh/host_keys/` | Отпечатки серверов, доверие при первом подключении и собственный `known_hosts` |
| `core/ssh/auth/` | Пароль, публичный ключ и keyboard-interactive |
| `core/ssh/channels/` | Каналы, окна передачи, выполнение команд, удалённая PTY и завершение сессий |
| `core/terminal/` | Разбор ANSI/VT-последовательностей, экран, курсор, прокрутка и ввод |
| `core/sftp/` | Бинарный протокол SFTP и операции с удалёнными файлами |
| `platform/ssh_secrets/` | Собственные адаптеры защищённого хранения платформ |
| `features/ssh/` | Профили, импорт ключей, подтверждение ключа сервера и панель подключений |

Имена каталогов предварительные: перед реализацией сверить их с текущей архитектурой проекта. Протокол не должен зависеть от Flutter-виджетов. Каждая сессия владеет своим сокетом, состоянием и ресурсами.

## Этап 0. Спецификация и криптографическая стратегия

1. Зафиксировать минимальный набор совместимых алгоритмов. Не обещать совместимость со всеми конфигурациями SSH-серверов.
2. Изучить SSH transport, authentication и connection protocols: RFC 4251–4254, актуальные дополнения для выбранных алгоритмов и форматов ключей.
3. Выбрать стратегию криптографии: системные API через собственные адаптеры либо собственная реализация. Не выбирать алгоритмы исключительно по простоте реализации.
4. Проверить наличие безопасного источника случайных чисел на каждой платформе. Не использовать обычный псевдослучайный генератор.
5. Определить лимиты пакетов, памяти, каналов, попыток аутентификации и таймаутов.

**Готовность:** документирована матрица алгоритмов и платформ, ограничения и способ проверки каждого примитива. Нет автоматического отката к слабым алгоритмам при ошибке подключения.

## Этап 1. Профили и ключи

Профиль содержит название, сервер, порт, пользователя, способ аутентификации и ссылку на приватный секрет. Секрет не должен попадать в сериализацию профиля.

- Добавление, изменение и удаление подключений.
- Импорт существующих ключей с проверкой формата и понятными ошибками для неподдерживаемых вариантов.
- Первый целевой формат — ключи Ed25519; поддержку зашифрованного OpenSSH-формата планировать отдельно, включая необходимую функцию получения ключа из парольной фразы.
- Генерацию ключей добавлять только после проверки криптографической реализации.
- Пароли по умолчанию запрашивать при подключении; сохранение делать явным выбором пользователя.
- Парольные фразы ключей хранить отдельно от ключей и только по выбору пользователя.

Защищённое хранение: Keychain на Apple, Android Keystore для защиты ключа шифрования, Windows Credential Manager/DPAPI. Для Linux сначала определить подходящий системный механизм: защищённое хранилище секретов доступно не на каждой установке. Не подменять его незаметно обычным файлом или SharedPreferences. Если защищённое хранение недоступно, разрешить сессионный ввод без сохранения секрета.

**Готовность:** секреты сохраняются и удаляются корректно, не появляются в логах, дампах запросов или файловой структуре проекта. Поведение без защищённого хранилища проверено отдельно.

## Этап 2. SSH transport и проверка сервера

Реализация: [ssh-stage-2.ru.md](ssh-stage-2.ru.md). Подключение и проверка сервера
доступны в настройках SSH; вход и команды относятся к этапу 3.

- Установление TCP-соединения и обмен версиями SSH.
- Декодирование потоковых пакетов с учётом частичных чтений и нескольких пакетов за одно чтение.
- Согласование алгоритмов, обмен ключами и проверка подписи сервера.
- Включение шифрования и проверки целостности; корректная обработка номеров пакетов.
- Повторный обмен ключами без потери данных открытых каналов.
- Отмена подключения, закрытие ресурсов и понятные ошибки сети.

Проверка сервера:

- Для нового сервера показывать имя, порт, алгоритм и SHA-256-отпечаток ключа.
- Разрешать явное доверие один раз либо сохранение доверия.
- При изменении известного ключа останавливать автоматическое подключение и показывать старый и новый отпечатки.
- Предусмотреть несколько допустимых ключей сервера и управляемую замену ключа.
- Сохранять доверие по нормализованному серверу и порту, не по названию профиля.
- Не отправлять пароль или аутентификационную подпись до успешной проверки сервера.

**Готовность:** неверная подпись, повреждённый пакет, превышение лимита или неподдерживаемый алгоритм завершают соединение безопасно. Смена ключа сервера не обходится автоматически.

## Этап 3. Аутентификация и первая команда

- Вход по паролю.
- Вход по публичному ключу с подписью запроса внутри клиента.
- Разблокирование зашифрованных приватных ключей без сохранения парольной фразы по умолчанию.
- Затем RSA с современными алгоритмами подписи и keyboard-interactive для дополнительных запросов сервера.
- Не повторять бесконечно отвергнутый способ входа; ограничить число попыток.
- Открытие канала `session`, запрос `exec`, отдельные stdout/stderr и получение exit status.
- Учёт окна передачи, backpressure, EOF и закрытия канала.

**Первый законченный результат:** пользователь выбирает профиль, проверяет ключ сервера, выполняет одну команду и получает результат. Этот этап ещё не является полноценным интерактивным терминалом.

## Этап 4. Удалённая PTY и терминал

Запрашивать PTY на сервере, затем открывать `shell`. Локальная оболочка и системная утилита SSH не требуются.

- Передавать тип терминала, размеры в символах и уведомления об изменении размера.
- Реализовать экран и основной набор ANSI/VT-последовательностей, цвета, перемещение курсора, очистку, scrollback и альтернативный экран.
- Корректно обрабатывать UTF-8, комбинируемые символы и ширину символов.
- Поддержать клавиши, выделение, копирование, вставку и bracketed paste.
- На мобильных устройствах добавить доступные `Ctrl`, `Esc`, `Tab`, стрелки и управление экранной клавиатурой.
- Добавить состояние подключения, явное отключение и предупреждение о разрыве сессии.
- Не выполнять команды повторно автоматически после переподключения.
- Обрабатывать уход приложения в фон: на мобильных ОС непрерывная работа сокета не гарантируется.

**Готовность:** интерактивные программы, например редактор и монитор процессов, работают с согласованным типом терминала; изменение размера не портит экран. Название `TERM` соответствует реализованным возможностям.

## Этап 5. SFTP

- Открывать SFTP subsystem через SSH-канал, без запуска локальной утилиты.
- Согласовать версию протокола и поддерживаемые расширения.
- Просмотр каталогов, чтение атрибутов, загрузка и скачивание с прогрессом и отменой.
- Ограниченное параллельное выполнение запросов с корректной связью request/response.
- Редактирование удалённых файлов с проверкой изменений на сервере перед перезаписью.
- Переименование, создание папок и удаление с явным подтверждением.
- Различать удалённые пути, локальные пути и символические ссылки.
- Для безопасной замены файла использовать временный файл и переименование, когда сервер это поддерживает; не обещать атомарность без поддержки сервера.

**Готовность:** отмена и сетевой обрыв не выдаются за успешную передачу; конфликт удалённого файла не приводит к тихой перезаписи.

## Этап 6. Дополнительные возможности

После стабильной базовой реализации рассмотреть SSH-туннели, несколько каналов в соединении, дополнительные форматы ключей и управление несколькими терминальными сессиями. Это отдельные расширения, не обязательная часть первого выпуска.

## Проверка перед выпуском

- Тестовые векторы для криптографии, форматов ключей и бинарных кодеков.
- Совместимость с независимыми SSH-серверами, включая OpenSSH как тестовый сервер. Использование сервера при проверке не означает зависимость клиента от системного `ssh`.
- Некорректные длины и сообщения, частичные пакеты, fuzzing парсеров, ограничения памяти и большие потоки данных.
- Неверный пароль, неверная подпись, смена ключа сервера, повторный обмен ключами и обрывы соединения.
- Проверки терминала, Unicode, изменения размера и мобильной клавиатуры.
- Проверки защищённого хранения и отсутствия секретов в логах на каждой платформе.
- Независимая проверка безопасности до использования с важными серверами. Прохождение функциональных тестов не заменяет проверку криптографической реализации.

## Порядок работ и границы обещаний

Реализовывать по этапам: спецификация → ключи и доверие → transport → аутентификация и одна команда → интерактивный терминал → SFTP.

Общая кодовая база уменьшает дублирование протокола и интерфейса, но не отменяет платформенные различия защищённого хранения и жизненного цикла приложения. Это отдельная подсистема IDE, а не небольшая UI-функция. Сроки оценивать после этапа 0; наиболее трудоёмкие части — криптография, зашифрованные форматы ключей и терминальная совместимость.

До подтверждения каждого этапа не заявлять полную совместимость с SSH, всеми серверами или всеми терминальными приложениями.
